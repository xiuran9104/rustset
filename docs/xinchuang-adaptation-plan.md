## 1. 项目概述

### 1.1 建设背景

RustSet 当前采用 Rust 后端（sqlx + PostgreSQL）、Vue 3 前端、Redis、Nginx 与 RustFS 对象存储，国密算法已有部分落地（SM3/SM4）。现有代码在数据库类型（`PgPool`）、SQL 方言、密钥管理和交付体系上与单一技术栈存在耦合，信创适配需要完成从"单一环境可运行"到"多平台产品能力"的转变。

本方案将信创适配作为多平台产品能力建设，而不是单一客户环境中的安装部署调整。改造完成后，平台应在规定的国产 CPU、操作系统、数据库、中间件、浏览器及国密环境下形成可重复构建、可迁移、可验证、可交付、可回退的完整能力。

### 1.2 建设目标

1. 建立一套业务代码支持多类信创环境的总体架构，避免按客户环境维护长期分叉。
2. 支持海光／兆芯 x86_64 与鲲鹏／飞腾 aarch64，覆盖银河麒麟和统信 UOS。
3. 支持达梦、人大金仓、openGauss 和 PostgreSQL，保证核心业务及事务、锁语义一致。
4. 完成 Redis、Nginx、对象存储等中间件的国产化目录适配能力。
5. 在已有 SM3/SM4 基础上，补齐国密 TLS、密钥管理、密文格式版本化与历史数据迁移能力，支持密评整改和送测。
6. 支持国产通用浏览器、国密浏览器及 WPS 办公软件。
7. 建立离线安装、升级、回滚、备份恢复、SBOM 和供应链安全交付体系。
8. 建立平台、数据库、中间件、国密和终端兼容的分层测试矩阵与验收门禁。

### 1.3 适配矩阵

| 维度 | 目标 | 说明 |
| --- | --- | --- |
| CPU | 海光 7000 系列、兆芯 KH 系列（x86_64）；鲲鹏 920、飞腾 D2000/S2500（aarch64） | **不含龙芯 LoongArch64** |
| 操作系统 | 银河麒麟高级服务器版 V10 SP2/SP3（rpm 系）；统信 UOS 服务器版 V20 1060a/1070e（deb 系） | 以实际采购版本为准，详细设计阶段冻结 |
| 数据库 | 达梦 DM8、人大金仓 KingbaseES V8R6、openGauss（集中式） | PostgreSQL 保留为开发基线 |
| 中间件 | Redis 或目录内替代（TongRDS）；Nginx 或目录内替代（Tengine/TongHttpServer）；对象存储 RustFS | 见 §4.3 |
| 浏览器与办公 | 麒麟/UOS 自带浏览器及主流国产浏览器（Chromium/Firefox 内核）、国密浏览器、WPS | 见 §4.5 |
| 密码合规 | 国密算法全面落地 + 商用密码应用安全性评估（密评，依据 GB/T 39786-2021） | 目标级别待决策（见 §5.5） |
| 运行架构 | x86_64、aarch64；systemd 与容器两种交付形态 | 见 §4.2、§4.6 |

### 1.4 范围边界

1. 龙芯 LoongArch64（rustls 的 aws-lc-rs/ring 在该架构编译支持差，如后续需要单独立项）。
2. 数据库分布式部署形态（openGauss 仅支持集中式单机/主备）。
3. 申威 SW64 等其他国产 CPU。
4. 国产中间件和浏览器的具体品牌、版本、部署形态以项目选型清单为准；本方案先定义适配接口、语义合同和验收要求。
5. 国密改造提供技术能力和密评配合，不以方案文档替代具备资质机构的测评结论。
6. 不通过禁用安全校验、隐藏不支持功能或伪造测试成功的方式形成表面兼容；不支持项必须显式登记并走范围变更。

### 1.5 建设原则

- **一套核心代码**：数据库方言、中间件适配器、密码提供方和部署 Profile 可插拔，业务代码不直接判断客户品牌。
- **先抽象，后适配**：任何数据库适配动手前，先完成 `PgPool` → 数据库门面的机械重构，把方言差异隔离在 `framework/database` 一处。
- **语义优先**：替换组件不仅要求接口可连接，还必须保持事务、锁、超时、重试等语义；"兼容 PostgreSQL"只能作为降低工作量的依据，不能作为免除测试的依据。
- **兼容演进**：历史数据、历史密文、历史令牌和现有 PostgreSQL 环境均要有迁移与回退路径。
- **安全前置**：密钥管理与密文格式缺陷优先整改，密码算法使用合规实现，不自行设计密码算法。
- **测试分层**：避免平台、数据库和中间件的全笛卡尔积重复测试，同时保证关键交付组合完整验收。
- **离线可交付**：所有生产依赖均应有受控来源、固定版本、完整性校验和离线获取方式。

### 2.2 关键差距

#### 2.2.1 数据库类型与方言耦合较深

**M1 已完成（2026-11-05）**：门面重构与运行时 SQL 可移植化落地——业务代码 0 处 `PgPool` 直接引用，错误分类经 `DbError` 统一，运行时 SQL 收敛到三库通用子集（剩余为显式标记的列级数组谓词、`ON CONFLICT`、`FOR UPDATE` 分支）。迁移目录仍固定为 `sql/postgresql`，`sql/{kingbase,opengauss,dm}` 由 `script/sql-translate` 产出（规则引擎 + 评审报告已就绪，产出入库待达梦真库验证 + 人工评审）。`FOR UPDATE`（21 处）对应的事务流仍是数据库替换中风险最高的部分，合同测试套件（§4.1.7）已在 PostgreSQL 通过，锁等待、死锁与隔离行为必须在四种数据库上分别证明。

#### 2.2.2 密钥管理与密文格式需要先行升级

**已完成（2026-11-05，§4.4.2）**：`enc:sm4:v3:` 认证密文格式（密钥版本 + HMAC-SM3 完整性标签，篡改可检测、失败关闭）、主密钥文件钥匙环（0600，与 `JWT_SECRET` 分离，版本化轮换就绪）、统一密封服务接入业务层、注册表驱动的批量 re-seal（v1 恒转、v2 在主密钥配置后转，分批幂等可重跑）。剩余：KMS/密码机硬件接入（§4.4.3 #2，M0 决策）、密钥管理制度文档（密评材料）。

#### 2.2.3 中间件与网关需要语义合同

Redis 当前使用的能力相对标准，协议兼容替换难度较低，但缓存不可用时的降级行为需要显式定义。Nginx 替换为 Tengine/TongHttpServer 时，反代的流式响应、大文件上传、长请求、真实客户端 IP 等行为必须逐项验收，不能以"页面能打开"代替。

#### 2.2.4 交付与验收体系需要扩展

现有迁移测试和部署脚本以 PostgreSQL 及通用 Linux 环境为中心，需要扩展为多数据库、多平台、多中间件和离线交付体系；备份恢复、上线切换、回退演练和验收证据链目前空白，需在本方案中补齐。

## 3. 总体目标架构

### 3.1 架构模型

采用"一套业务核心＋三类适配层＋多种交付 Profile"：

```text
┌──────────────────────────────────────────────┐
│                RustSet 业务核心               │
│            各业务模块（62 个数据访问文件）      │
└───────────────────┬──────────────────────────┘
                    │
        ┌───────────┼───────────┐
        │           │           │
┌───────▼──────┐ ┌──▼─────────┐ ┌▼──────────────┐
│ 数据库适配层  │ │ 密码提供方  │ │ 平台与中间件层 │
│ PostgreSQL   │ │ Standard   │ │ x86_64/aarch64 │
│ 金仓/openGauss│ │ GM         │ │ 麒麟/UOS       │
│ 达梦(ODBC)   │ │ KMS/密码机  │ │ 缓存/网关/存储 │
└──────────────┘ └────────────┘ └────────────────┘
                    │
        ┌───────────┴────────────┐
        │ 安装、迁移、测试与交付 Profile │
        └────────────────────────┘
```

### 3.2 代码分支与版本策略

1. 不为达梦、金仓、openGauss 或不同国产 OS 建立长期业务分支。
2. 数据库差异通过门面实现、方言模块和独立迁移链管理；`sql/postgresql` 仍是唯一手写源头，其余方言目录由翻译工具产出 + 人工评审。
3. 国密与通用密码实现通过统一密码服务接口管理，算法与密钥版本标识进入密文格式。
4. 平台差异通过构建目标、安装包和部署 Profile 管理。
5. 所有适配实现进入同一 CI 门禁，避免某个目标环境长期失修。

### 3.3 配置模型建议

以下为规划配置，不代表现有变量已经存在：

```text
DB_FLAVOR=postgresql|kingbase|opengauss|dm
DATABASE_URL=<按适配器定义>
CACHE_PROVIDER=redis|tongrds
CRYPTO_PROVIDER=standard|gm
KEY_MANAGEMENT_PROVIDER=local-file|kms|hsm
TLS_PROFILE=standard|gm
```

配置加载时必须校验 provider 与 URL、证书、密钥及功能能力是否匹配；不支持的组合应启动失败并给出明确错误，不得在运行时静默降级。

## 4. 详细改造方案

### 4.1 多数据库适配（核心，关键路径）

#### 4.1.1 数据库门面（M1 前置重构）

在 `crates/framework/database` 内新增门面层：

- `DbPool`：连接池门面。PG 家族实现包装 `sqlx::PgPool`；达梦实现包装 ODBC 连接池（§4.1.6）。
- `DbRow`：行读取门面。统一 `get::<T>()` 覆盖现有用到的类型集（`i64`、`String`、`bool`、`f64`、`chrono::DateTime<Utc>`、`uuid::Uuid`、`serde_json::Value`）。达梦侧 ODBC 读出的字符串/字节在此层解码。
- `DbTransaction`：事务句柄，覆盖现有 `FOR UPDATE`（21 处）对应的事务流。
- `DatabaseFlavor` 枚举：`Postgres | Kingbase | OpenGauss | Dameng`，由 `DATABASE_URL` scheme 或 `DB_FLAVOR` 环境变量决定，供少数确实需要方言分支的 SQL 使用。
- 迁移执行器按 flavor 选择 `sql/{postgresql,kingbase,opengauss,dm}` 目录。
- **错误分类统一**：唯一约束冲突、外键冲突、死锁、锁等待超时、连接中断在各适配器上映射为同一组门面错误，业务层不得直接匹配 sqlx/ODBC 原生错误码。对不支持的能力显式报错，不得静默忽略。

业务代码改动是机械的：213 处 `PgPool` 引用替换为 `DbPool`，查询字符串不变。**这是一次性成本，必须最先做，否则每个数据库适配都要重复侵入 62 个文件。**

#### 4.1.2 方言差异与翻译规则

| PG 构造 | 金仓 V8R6 | openGauss | 达梦 DM8 | 处理策略 |
| --- | --- | --- | --- | --- |
| `jsonb` 列 | 兼容（PG 内核） | 兼容 | 无 → `TEXT`/`CLOB`，应用侧 serde_json 编解码 | 类型由门面映射；达梦翻译为 TEXT |
| `uuid` 列 | 兼容 | 兼容 | 无 → `CHAR(36)` | 翻译规则；ID 已应用侧生成 |
| `ON CONFLICT` | 支持 | 支持 | 无 → `MERGE INTO` | 迁移×1 + 运行时×12，达梦分支改写 |
| `ilike` | 支持 | 支持 | 无 → `LIKE UPPER()` | 源码直接改成 `LIKE UPPER()`（三库通用） |
| `ANY($1)` 数组绑定 | 支持 | 支持 | 无 | 源码改为 `IN (…)` 展开（门面提供 `expand_in()` 工具） |
| `::jsonb`/`::uuid` cast | 兼容 | 兼容 | 无 | 源码去掉 cast，绑定参数类型由门面处理 |
| `interval` | 兼容 | 兼容 | 支持但语义有差 | 运行时×27 处改用 chrono 计算 + 传数值；迁移×7 逐条翻译 |
| `now()` | 兼容 | 兼容 | 兼容 | 不动（285 处） |
| `EXCLUDE` 约束 | 兼容 | 兼容 | 无 | 唯一 1 处（0035 租户唯一）→ 唯一索引或应用保证 |
| gin 索引 | 兼容 | 兼容 | 无 | 唯一 1 处 → 普通索引，功能降级登记 |
| `to_char`/`EXTRACT` | 兼容 | 兼容 | 部分兼容 | 运行时 10 处改 chrono 格式化后传参 |
| serial/identity | 兼容 | 兼容 | `IDENTITY(1,1)` | 翻译规则 |

#### 4.1.3 运行时 SQL 可移植化（M1 内容）

按 §4.1.2 把源码里的 PG 专有写法改成三库通用子集，预计触及 150–200 处查询点。完成后，运行时 SQL 仅剩三类合法方言分支：`ON CONFLICT`（达梦走 MERGE 分支）、jsonb 读写（门面处理）、极少数日期运算。复杂查询允许数据库特定实现，不追求不切实际的"一条 SQL 跑四库"。

验收：`cargo test --workspace` 全绿 + 纯 PG 环境全功能回归不劣化。

#### 4.1.4 金仓 KingbaseES（M1，最低成本）

- 实例以 **PG 兼容模式**建库（金仓支持 Oracle/PG/MySQL 多兼容模式，必须选 PG 模式）。
- sqlx PG 协议直连；重点回归 uuid/jsonb 的 OID 扩展类型编解码、`FOR UPDATE`、事务隔离行为。
- `sql/kingbase/`：`0001` 由"PG 参考库 → 金仓逻辑导出 → 比对"生成，`0002+` 直接复用 `sql/postgresql`（金仓兼容则符号链接或拷贝，由翻译工具判断）。

#### 4.1.5 openGauss（M2）

- **认证是第一坑**：openGauss 默认 `password_encryption_type=2`（sha256），libpq 系客户端（含 sqlx）不支持。方案：建库时为应用账号设 `password_encryption_type=1`（MD5）或 `0`，安装文档写死该步骤。
- 其余与 PG 差异（线程池、`enable_opfusion` 等）对应用透明；全量回归 + 压测一轮。

#### 4.1.6 达梦 DM8（M3，最高成本与风险）

达梦无 PG 线协议，官方无 Rust 驱动。路线：

1. **连接层**：`odbc-api` crate + 达梦随介质提供的 ODBC 驱动（`libdodbc.so`），实现 `DbPool`/`DbRow`/`DbTransaction`。备选：达梦 DPI（C 接口）自行 FFI，成本更高，仅在 ODBC 质量不达标时启用。
2. **类型映射**：`uuid→CHAR(36)`、`jsonb→TEXT`、`timestamptz→TIMESTAMP(6) WITH TIME ZONE`、`boolean→BIT`、`bigserial→IDENTITY`、`interval→数值列`。
3. **迁移链**：新增 `script/sql-translate`（Rust 小工具）：输入 `sql/postgresql/*.sql`，输出达梦方言（§4.1.2 规则 + `CREATE INDEX IF NOT EXISTS` 等 DDL 幂等改写）。`0001_initial.sql` 走流水线：PG 参考库全量导出 → 翻译 → 达梦导入 → **行数与抽样 checksum 比对**（34.6 万行不允许人工目检）。
4. **并发与驱动质量**：ODBC 连接池参数压测调优；`FOR UPDATE`、死锁、超时行为专项测试。
5. 交付物：DM ODBC 驱动 so 文件进入离线包清单，安装脚本配置 `odbcinst.ini`。

#### 4.1.7 事务与锁语义合同

以下不变量必须在四种数据库上分别证明，构成数据库合同测试的核心：

1. 多步写入在同一事务中提交，部分失败时完整回滚，不出现半提交状态。
2. `FOR UPDATE` 对应的 21 处事务流在并发下互斥正确，锁等待、死锁检测与超时行为符合预期。
3. 唯一约束冲突被统一映射为业务可识别的冲突错误，不因数据库差异变成内部错误。
4. 隔离级别在各库显式声明并验证，不以数据库默认值作为行为依据。
5. 数据库连接中断、慢查询与恢复期间，不伪造写入成功，恢复后无重复提交。

#### 4.1.8 迁移与测试基础设施

- `sql/` 目录结构：`postgresql/`（手写源头）、`kingbase/`、`opengauss/`、`dm/`（生成 + 评审后入库）。
- 每种数据库均支持空库初始化、老版本升级和迁移历史保护；国产数据库迁移必须幂等，并记录版本、执行时间和失败原因。
- 启动时检测"已有业务表但无迁移历史"的危险状态，拒绝直接覆盖。
- `script/test-database-migrations.sh` 增加 `--db <flavor>`：起对应容器（金仓/openGauss/DM8 官方镜像）执行"空库到最新 schema + 基线数据"验收。
- `crates/framework/database/tests/migrations.rs` 的迁移计数断言按四套目录分别校验。
- 提供 schema 对比、表数量、行数、关键字段摘要和抽样业务校验；数据迁移支持断点记录、重复执行保护、失败清单和重新执行失败批次。
- AGENTS.md 的数据库工作流同步更新：**新迁移提交时必须同时产出并验证四个方言目录**。
- CI 矩阵：`{x86_64, aarch64} × {PG, 金仓, openGauss, DM8}` 的后端全量测试（镜像许可注意国产库容器在 CI 的授权条款）。

### 4.2 CPU/OS 适配与构建交付（M4，可与 M1 并行）

#### 4.2.1 编译

- 双 target：`x86_64-unknown-linux-gnu`、`aarch64-unknown-linux-gnu`。
- glibc 基线：麒麟 V10 与 UOS V20 均为 glibc 2.28 级别 → 统一在 glibc ≤ 2.28 的构建容器（对标 manylinux_2_28）内编译，不在目标机编译。
- aws-lc-rs/ring、libsm、calamine、zip 等依赖在双架构均可用；aarch64 优先用原生构建机（QEMU 模拟编译 Rust 过慢），次选 `cross-rs` 交叉；交叉编译只作为 CI 检查，不替代目标机验证。
- 构建即验：CI 增加双架构 `cargo build --release` + `cargo test`。
- 分别在麒麟和统信 UOS 目标环境验证动态链接、证书、时区、中文字体和 systemd 行为。

#### 4.2.2 前端

- 纯静态产物与 CPU 架构无关：**只在 x86_64 构建机出一份 `dist`**，双架构共用；不在国产环境装 bun。
- 国产浏览器（Chromium/Firefox 内核）天然兼容 Vue3/AntD；补一份《浏览器兼容声明》+ 常见国产浏览器截图回归（麒麟自带浏览器、UOS 浏览器、360/奇安信浏览器），详见 §4.5。

#### 4.2.3 安装与运行改造

1. 完善麒麟／统信的 systemd unit、用户权限、目录权限、环境文件和日志轮转；验证开机自启、`Restart=always`、journald 中文日志。
2. 容器化交付使用经过评审的目标基础镜像，保留 non-root、只读根文件系统等安全约束。
3. 安装脚本检测 CPU、OS、glibc、依赖、端口、磁盘和证书，不满足条件时在修改系统前退出。
4. 提供安装、升级、回滚和卸载日志，不在升级脚本中自动删除数据库或历史备份。

#### 4.2.4 平台交付物

- 四类"CPU＋OS"组合的离线 tarball 安装包及对应容器镜像。
- 每 OS × CPU 组合跑认证清单：systemd 托管启停、开机自启、日志、时区/字符集、防火墙端口、升级安装（迁移链在旧库上滚动）。
- 依赖清单、SHA256 校验值、SBOM 和安装手册（见 §4.6）。

#### 4.3.1 缓存语义合同

- 覆盖现有用到的 GET、SETEX、DEL、SCAN、INCR、EXPIRE、TTL 等命令，验证 key 编码、批量删除、游标扫描和连接异常行为。

- 若采用国产集群模式，验证重定向、跨 slot、连接池和故障切换。

#### 4.3.2 网关语义合同

- 国产网关必须支持流式响应、大文件上传、长请求、摘流和健康检查。
- 保留关闭代理缓冲、合理读超时、`X-Forwarded-For` 真实客户端 IP 传递的要求。
- 管理端口与审计接口不对外暴露；替换后告警与日志字段语义尽量保持稳定。

### 4.4 国密与密评（M5–M6）

依据：GB/T 39786-2021《信息安全技术 信息系统密码应用基本要求》（通常伴随等保三级同步做）。

#### 4.4.1 已具备

- 摘要/完整性：SM3、HMAC-SM3（含会话令牌签名）。
- 存储保密：SM4-CBC 落盘密封（`enc:sm4:v2:`），`0018` 已完成存量 XOR→SM4 re-seal。
- 口令：PBKDF2-HMAC-SM3（16384 轮）。
- 身份：SM3 派生 per-user `identity_uuid`。

#### 4.4.2 密码服务抽象与密文格式升级

建立统一密码服务接口，覆盖数据加解密、密钥版本查询与轮换、消息认证、摘要与口令派生。业务模块不直接选择底层算法库，也不自行实现 SM2／SM3／SM4。

1. 密文格式升版（`enc:sm4:v3:`）：格式至少包含格式版本、算法标识、**密钥版本**、随机 nonce/IV、密文和**完整性认证标签**（如 SM4-GCM 或 CBC+HMAC-SM3 封装），篡改必须可检测。
2. 数据密钥与主密钥分离，主密钥由 KMS／密码机或经过评审的密钥管理机制保护；不再允许生产环境默认回退到环境变量派生或内置常量。
3. 提供 `v2` 历史数据识别、解密、重加密、校验和回滚工具；迁移分批、可重复执行、带失败清单，不在单个大事务中处理全部历史数据。
4. 令牌格式增加算法版本标识，设置旧令牌迁移窗口和强制失效机制；HMAC-SM3 已满足完整性要求，JWT 是否升级 SM2 签名视测评口径决策。
5. S3 SigV4 等第三方协议所需 SHA-256/HMAC 保持协议实现，不与业务国密要求混淆。

#### 4.4.3 缺口与整改

| # | 缺口 | 整改 | 备注 |
| --- | --- | --- | --- |
| 1 | 传输层无国密 TLS（TLCP，GB/T 38656-2020） | 入口网关用 **Tengine + 铜锁（TongsSSL）** 终结国密双证书（SM2 签名证书 + SM2 加密证书），后端维持现状 | 应用代码不动；浏览器需国密支持的场景由国密安全浏览器/客户端网关承接 |
| 2 | 纯软件密码模块无商用密码产品认证证书 | 决策点：接 SDF 密码卡/加密机（GM/T 0018 接口），或采购有认证的软件密码模块 | `gm` crate 抽象 `Sm4Provider`/`RandomProvider` trait，预留硬件实现位；纯软件作为非密评场景默认 |
| 3 | 密钥管理薄弱：SM4 密钥 = SM3(环境变量密钥) 派生，无独立保管与轮换 | 第一步：独立主密钥文件（0600，启动加载，与 JWT_SECRET 分离）；第二步：re-seal 升版机制支持密钥轮换（沿用 `legacy_v1` → `sm4:v2` 的既有先例，扩展 `v3`） | 密钥生成、分发、归档、销毁流程写入管理制度（密评文档部分）；密钥备份必须受控，禁止明文进入普通备份目录 |
| 4 | SM2 未使用 | TLS 双证书必用（#1）；JWT 是否升级 SM2 签名视测评口径——HMAC-SM3 已满足完整性要求，建议保留并备注说明 | libsm 0.6.1 自带 sm2 模块，成本低，可选项 |
| 5 | 随机数来自 OS（getrandom） | 一般可接受；若测评要求 GM/T 0005 检测，通过 SDF 硬件取随机 | 随 #2 决策联动 |
| 6 | 审计留存期未核对（等保要求 ≥6 个月） | 核对 audit 日志落盘/轮转策略，不足则补；审计完整性保护增加 SM3 算法标识 | 工作量小 |
| 7 | 国密 TLS 互操作未验证 | 验证证书链、双证书、证书轮换、过期、吊销和国密浏览器互操作；明文内网链路只能作为经安全评审的明确配置，不能作为故障时自动降级行为 | 与 §4.5 浏览器验证合并执行 |

#### 4.4.4 密评流程与材料

选机构 → 方案设计评审（本节作为输入）→ 现场测评 → 整改 → 报告。**硬件密码设备采购周期通常 4–8 周，须在 M0 启动**。

交付材料：密码应用方案、算法与密钥清单、证书清单、密钥生命周期说明、密码模块／产品证明、调用位置说明、测试报告和整改记录。最终合规结论以具备资质的测评机构结果为准。

### 4.5 国产浏览器与 WPS 适配

1. 冻结浏览器品牌、版本和内核基线；调整前端 browserslist／构建目标，避免仅按常见桌面 Chrome 验证。
2. 建立浏览器自动化与人工兼容用例，覆盖登录、菜单、表格、图表、表单、打印、上传下载与流式响应；清理依赖特定 UA 的功能判断，优先使用能力检测。
3. 验证国密 HTTPS 下的证书、混合内容、跨域和流式响应（与国密浏览器互操作合并测试）。
4. 验证 WPS 打开导出 Excel／CSV／压缩包时的中文、日期、数字、公式、样式和大文件名（calamine/zip 相关导入导出路径逐项过一遍）。
5. 所有用例留存版本、截图／日志和结论，作为验收证据。

### 4.6 离线部署与供应链

1. **离线 tarball（基线形态）**：`rustset-<版本>-<arch>.tar.gz`，含 gateway 二进制、web dist、DM ODBC so（按需）、`install.sh`（解压、写 systemd、载入 env）、SHA256 清单。
2. **容器形态**：gateway 与 RustFS 镜像用 buildx 出 `linux/amd64` + `linux/arm64` 双 manifest，增加架构节点亲和性，防止 ARM64 节点拉取错误架构镜像；compose 模板按目标库替换 postgres 服务为金仓/openGauss/DM8 对应部署；**NATS 从交付物移除**（代码零引用），Redis 按目录决策保留或换 TongRDS。
3. 离线可复现构建：`cargo vendor` + `.cargo/config.toml`（目前缺失，需补）、bun 锁定与 `node_modules` 缓存内网化、私有镜像仓库或 U 盘介质交付。
4. 建立内部容器镜像、crates、npm 和系统包镜像源；所有依赖固定版本并保存校验值，禁止使用构建时不受控的最新版本。
5. 镜像与安装包生成 SBOM，执行漏洞、许可证和恶意代码扫描；交付物使用受控签名机制并提供验证方法。
6. 离线环境准备证书、中文字体等运行资源；安装、升级和回滚不得依赖访问公网。
7. 可选：麒麟 rpm / UOS deb（fpm 打包），二期视客户要求。

### 4.7 备份、恢复与运维

1. 为四种数据库分别提供备份恢复工具和脚本；保留数据库＋对象存储同一恢复集的设计，不拼接不同恢复点产物。
2. 为对象存储实现对象清单、摘要校验和恢复审计，保持数据库对象引用与存储恢复点一致。
3. 密钥、证书分别定义备份与重建方式；密钥备份必须受控，禁止以明文进入普通备份目录。
4. 制定恢复演练：停止写入、恢复数据库、恢复对象、校验引用、启动服务、抽查业务。
5. 监控指标名称、日志字段和告警语义尽量保持稳定，降低运维平台替换成本；审计日志留存期满足等保要求。

## 6. 测试与验收方案

### 6.1 分层测试策略

#### 第一层：平台构建测试

四种组合全部执行：

| 组合 | CPU | OS | 必测内容 |
| --- | --- | --- | --- |
| P1 | x86_64 | 麒麟 | 构建、安装、启动、升级、回滚 |
| P2 | x86_64 | 统信 UOS | 构建、安装、启动、升级、回滚 |
| P3 | aarch64 | 麒麟 | 构建、安装、启动、升级、回滚 |
| P4 | aarch64 | 统信 UOS | 构建、安装、启动、升级、回滚 |

#### 第二层：数据库合同测试

四种数据库运行同一套测试合同：

- 数据访问 CRUD 与复杂查询；类型、中文、JSON、时间和大整数。
- 事务提交、回滚、隔离与锁等待；唯一约束冲突、死锁、超时的统一错误分类（§4.1.7）。
- 空库初始化、历史版本升级和"有表无迁移历史"危险状态拒绝。
- `FOR UPDATE` 事务流并发互斥、连接中断恢复后不重复提交。
- 数据迁移、校验、备份和恢复。

x86_64 执行四库全量测试；aarch64 执行四库核心全量回归及实际交付组合的完整验收。

#### 第三层：完整交付组合测试

按实际选型形成完整组合，至少覆盖：

- 国产 OS＋国产数据库＋国产中间件。
- 国产数据库＋国密 TLS＋KMS／密码机。
- 国密浏览器＋国产网关＋流式响应／大文件上传。
- 离线环境＋干净安装与升级。
- 数据库与对象存储故障及一致性恢复。

### 6.2 功能验收

1. 现有核心功能与端到端用例在目标环境全部通过。
2. 登录、权限、核心业务流程、文件上传下载等关键业务通过。
3. 四库空库初始化与升级结果符合各自 schema 基线。
4. 迁移前后表、行数、关键字段和业务抽样一致，失败记录均有处置结果。
5. 浏览器和 WPS 用例全部有版本、截图／日志和结论。

### 6.3 可靠性与故障验收

必须注入并验证：

- 数据库连接中断、慢查询、死锁和恢复。
- 缓存不可用与恢复，降级行为符合 §4.3.1 的显式定义。
- 网关重启、长请求中断与大文件上传失败。
- 对象存储超时、重启和大对象失败。
- 密钥不可用、证书过期和国密 TLS 握手失败。
- 服务停止、重启及升级回滚。

### 6.4 安全与国密验收

1. 敏感字段密文包含算法与密钥版本，篡改能够被检测。
2. 密钥不进入代码、普通日志或普通备份。
3. 密钥轮换、历史密文重加密和回滚演练通过。
4. SM2／SM3／SM4 和国密 TLS 使用合规实现并完成互操作验证。
5. 历史 `enc:sm4:v2` 密文和历史口令仍可受控验证。
6. 管理端口不对外暴露；完成漏洞扫描、依赖许可证检查和交付物签名校验。

### 6.5 性能验收

1. 在详细设计阶段冻结数据量、并发量、文件大小和时延／吞吐阈值。
2. 四种数据库分别保存执行计划和性能报告，不仅比较平均响应时间。
3. 覆盖登录、列表查询、复杂检索、文件上传下载和 Excel 导入导出。
4. 对 SM4 加解密、SM2 验签和国密 TLS 进行独立性能测试；对达梦 ODBC 连接池做专项压测。
5. 性能未达阈值时必须形成分析、整改和复测记录，不以硬件差异直接豁免。

### 6.6 备份恢复与回退验收

1. 每种数据库至少完成一次空环境恢复演练。
2. 数据库与对象存储按同一恢复集恢复，对象引用审计通过。
3. 升级前保留数据库、配置、密钥和安装包回退点。
4. 切换失败时可以恢复原数据库流量或原版本服务。
5. 回退过程不丢失已确认业务数据、不覆盖新产生的有效数据。
6. 恢复后执行登录、业务抽查、文件下载和日志检查。

### 6.7 验收通过条件

- 范围内必测项执行率和通过率均为 100%。
- 无未关闭的阻断级或严重级缺陷。
- 所有不支持项均有书面范围变更，不以口头说明代替。
- 数据迁移、备份恢复、故障注入和回退演练均有可复核证据。
- 安装包、镜像、SBOM、签名、手册和测试报告齐套。
- 密评相关问题有整改记录；最终测评结论由相应测评机构出具。

## 7. 数据迁移与上线切换

### 7.1 迁移流程

1. 冻结源库版本、字符集、数据量和业务基线。
2. 执行全量备份并验证可恢复性。
3. 在目标库执行 schema 初始化与兼容性检查。
4. 进行全量数据迁移，输出表级与字段级报告（`0001` 基线行走 §4.1.6 流水线）。
5. 按增量方案同步迁移期间变化，或进入受控停写窗口。
6. 执行行数、关键摘要、序列、对象引用和业务抽样校验。
7. 使用目标数据库运行只读验证和核心冒烟。
8. 切换应用配置并观察错误率、慢查询和性能。
9. 保留源库只读与回退窗口，确认稳定后再按流程处置旧环境。

### 7.2 国密数据迁移

国密密文迁移与数据库迁移解耦执行，避免同时改变存储位置和加密格式导致问题不可定位：

1. 先完成原环境新加密能力（v3 格式、主密钥文件）及历史密文迁移演练。
2. 数据库迁移时保持密文版本和密钥版本不变。
3. 切换后验证密钥可用性和历史密文读取。
4. 再按批次完成国密重加密和旧密钥下线。

### 7.3 回退原则

- 回退以经过验证的备份和源库为基础，不依赖临时手工 SQL。
- 切换后若允许源库回写，必须有双向同步或明确数据处置方案；否则回退前停写并评估新数据。
- 回退不自动删除目标库，保留证据供问题分析。
- 密钥、证书和中间件配置均纳入同一切换清单。

5. 安全算法、密钥管理和降级行为必须经过安全评审。
6. 不支持的功能必须显式记录，不允许伪造测试成功或省略失败日志。
7. 发布前重新验证四类平台安装包、离线部署和恢复演练。
8. 具体国产产品升级后，按变更范围重新执行兼容认证。
